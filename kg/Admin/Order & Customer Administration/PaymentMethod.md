# PaymentMethod

The platform's payment-method reference list — Cash, Wallet, Online, Orange, OnlineWallet — each scoped to
the countries it is offered in. A short entity: two names, an active flag, and a country collection
(`Shared/TalabatkLogic/TalabatkModels/PaymentMethod.cs`).

**The thing to understand before changing anything here is that this table's primary keys are load-bearing
constants.** Roughly two dozen decision points in the order, refund, compensation and item-replacement
paths do not read this table at all — they compare `OrderPayments.PaymentMethodId` against the hard-coded
`PaymentMethods` enum. The table supplies the *names* the apps display; the enum supplies the *behaviour*.
Nothing ties the two together, and nothing would report it if they diverged (🟡 #632).

## Why the enum coupling matters

The five enum members and the five expected table rows are two independent facts that happen to agree. The
agreement is never asserted:

```
TA_PaymentMethods rows  ──displays──>  ArabicName / EnglishName        (this entity)
        │
        └── PaymentMethodId ══ (int)PaymentMethods.X ══> every money-path branch   (~24 sites)
                              (nothing checks this)
```

Two consequences follow.

**A new row would be behaviourally invisible.** The key is database-generated (rule 11) and there is no
create path (rule 5), so today this cannot happen through the API. If a row were inserted by migration or
by hand, its id would match no enum member, and every branch of the form
`PaymentMethodId == (int)PaymentMethods.Online` would simply be false. An order paid by that method would
fall through the online-payment handling, the wallet handling and the cash handling alike — with no error
anywhere, because none of those sites has an `else` that objects to an unknown method.

**The enum's numeric values collide with a second enum stored on the same row.** `PaymentMethods.Online`
is 3; `OrderPaymentStatus.Failed` is also 3 (`Shared/TalabatkLogic/Enum/OrderPaymentStatus.cs:8`). Both are
persisted as bare `int` columns on `OrderPayment`, so nothing in the type system distinguishes them. That is
not hypothetical: `PayMobCallBackCommand.cs:256` compares `PaymentStatusId` against
`(int)PaymentMethods.Online`, which means "status is Failed" — see ⚪ #631. That method is dead today, which
is the only reason the defect is not live.

## Correcting the earlier reading of this entity

An earlier pass recorded `PaymentMethod` as "a clean, positive example — `Instance` and `Update` validate
identically and stay in sync". The validation *is* identical, but the reason is that **`Instance` is never
called** (rule 5). There is no create/update pair being kept in sync; there is one live method and one dead
one. The genuinely good properties are elsewhere and are still worth keeping: failure is representable
(rule 4), and `UpdateCountries` computes its add-set from a snapshot taken before the removals (rule 8),
which is the correct order and the same shape as `City.UpdateCity`'s price-tier handling and
`DeliveryMen.Update`'s zone handling.

## Open Questions

- [x] **Is `PaymentMethodCountries` a simple join entity?** Yes — two ids, two navigations, one factory that
      sets only the country (`Shared/TalabatkLogic/TalabatkModels/PaymentMethodCountries.cs:21-27`), and a
      composite key in the map.
- [ ] Should the seeded ids be pinned — `ValueGeneratedNever()` plus `HasData`, or a check at startup that
      every enum member has a matching row? Either would turn #632 from a convention into a guarantee.
- [ ] Should the ~24 comparison sites read a single helper rather than the raw enum, so an unknown method
      throws instead of falling through every branch?
- [ ] `IsActive` is stored on the method globally while availability is also per-country — which wins when
      an active method lists a country it should not serve, or vice versa? Not traced.
- [ ] Rule 3's message ("Country ID must be a positive number") does not describe its check. Are negative or
      zero country ids meant to be rejected too? Nothing rejects them today.
